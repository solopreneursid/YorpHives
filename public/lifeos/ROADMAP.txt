LifeOS — Product & Engineering Roadmap
Parent platform: YorpHives
Product route: /lifeos/
Architecture decision: the current browser/PWA build is a concept and workflow prototype, NOT the intended final application.

PRODUCT VISION
LifeOS helps people turn intentions into consistent action: understand what matters today, make progress on meaningful goals, build routines without guilt, and stay in control of their plans and data.

PRODUCT PRINCIPLES
- Make the Today experience the center of the product: a realistic daily plan, a few clear priorities, and a useful next action.
- Connect daily tasks to goals and milestones instead of treating every module as a separate silo.
- Start new workspaces empty. Demo content must be opt-in and clearly marked.
- Prefer reliable local-first workflows and portable backups before accounts, sync, or AI.
- Keep secondary areas discoverable but do not let them overwhelm the main navigation.
- Add features only when they strengthen the core experience or are supported by user demand.
- Never describe planned, unbuilt, or untested capabilities as available.

Build LifeOS as a polished, installable, cross-platform personal productivity application. The user should be able to use the core app without a browser tab, keep core data on-device, and later opt into secure synchronization across their own devices. YorpHives remains the parent platform for discovery, product information, release notes, support, and downloads.

RECOMMENDED TECHNICAL DIRECTION
- App client: Flutter/Dart, using a single shared application codebase for Android and iOS first, followed by Windows, macOS and Linux after the core experience is stable.
- Local database: SQLite through a maintained Flutter database layer (evaluate Drift or an equivalent maintained package before implementation). Local-first CRUD must work without network access.
- App architecture: feature modules (Today, Tasks, Habits, Goals, Money, Study & Career, Notes/Documents, Calendar/Reminders, Insights, Settings); repository layer between UI and persistence; migrations and schema versioning from the first database version.
- Platform integrations: native notifications, app lifecycle, secure storage for credentials/tokens, file picking and sharing, app icons, deep links, accessibility and responsive layouts implemented through supported platform plugins.
- Sync backend: defer until local data model and migration strategy are stable. Use supported authentication and authenticated APIs. Enforce ownership on the server; never trust a client-supplied user ID.
- Web: keep YorpHives /lifeos/ as a product landing page and optional lightweight companion/prototype. Do not treat PWA installation as the final delivery strategy.
- Distribution: Android signed APK/AAB for testing and store release; iOS signed builds through Apple's distribution flow; desktop installers/packages for Windows, macOS and Linux. These are build/release deliverables and are NOT currently produced.

WHY THIS DIRECTION
- It makes app installation, native notifications, file access and OS integration first-class capabilities.
- SQLite provides reliable structured local storage and supports offline-first use.
- One Flutter codebase limits duplication for a solo founder.
- Shipping Android first allows validation before maintaining every desktop/mobile platform.
- The web landing page remains integrated into YorpHives without forcing the actual product to run only in a browser.

PHASE 0 — PRODUCT AND TECHNICAL FOUNDATION
- Keep the current PWA as a working prototype/reference; do not discard it until feature parity and data export are verified.
- Freeze a canonical feature inventory and domain model: tasks/projects, dated habit check-ins, goals/milestones, expenses/subscriptions, study/career items, reminders, notes/document references and settings.
- Define shared IDs, timestamps, time-zone rules, recurring schedules, deletion semantics, currency handling, validation, and JSON export/import format.
- Define quality bars: automated tests, accessibility, database migration tests, restore tests, offline tests, backup compatibility, and release signing.
- Added the first portable backup contract at /lifeos/DATA-CONTRACT-v1.json and migration/safety rules at /lifeos/DATA-MIGRATION-CONTRACT.txt.
- The browser prototype exports a named, versioned backup envelope; import validates workspace version, item shape, required IDs/types/titles, duplicate IDs and a 10 MB file limit before confirmation. Legacy version-1 exports remain accepted.
- Destructive item deletion and workspace reset now offer a short-lived Undo action, with save-failure handling. This UI behavior still requires end-to-end browser testing before it is treated as fully verified.
- Prototype Flutter toolchain and SQLite package in a development environment before choosing final package versions.
- Do not mark the product as Available until installable builds pass device testing.

PHASE 1 — NATIVE APP FOUNDATION (ANDROID FIRST)
- A separate minimal Flutter source scaffold has been prepared for Android-first work; progress and unverified items are tracked in /lifeos/NATIVE-STARTER-STATUS.txt. It is not compiled or release-ready yet.
- Create the Flutter application source as a native application codebase, kept within the YorpHives product's version-control/release process. Do not create a separate YorpHives product or duplicate catalogue entry.
- Implement app shell, navigation, design tokens, themes, localization-ready text, accessible components, error/empty/loading states, and first-run onboarding.
- Add SQLite persistence, versioned migrations, repository interfaces and unit/widget/integration tests.
- Add export/import with schema versioning and safe validation; never silently overwrite user data.
- Provide sample data as an optional demo, not mixed into a user's real workspace by default.
- Build a signed Android test package and test installation, upgrade, restart, offline use, backup and restore on real devices. Publish it through /lifeos/downloads.html only after release metadata, checksum and acceptance evidence are recorded.
- Make the user-facing release a single obvious platform-specific download action; keep installation instructions and checksum/version details beside the artifact. Never link to a missing or unverified package.

PHASE 2 — CORE DAILY WORKFLOWS
- Today dashboard with priorities, overdue items, upcoming commitments and an end-of-day review.
- Tasks and projects with priorities, due dates, subtasks, recurrence, filters and reliable completion history.
- Habits with schedules, dated check-ins, streaks and a history/calendar view.
- Goals with milestones and progress history.
- Money with manual expenses, categories, monthly budgets and recurring subscription reminders. No bank connection in this phase.
- Study/career plans, searchable notes, reminders and document references.
- Search, quick capture, undo for destructive changes, keyboard navigation on desktop, and helpful empty states.
- Native local notifications with explicit permissions and per-reminder controls.
- Track feature-level tests and usability issues before adding new modules.

PHASE 3 — DESKTOP AND SECOND MOBILE PLATFORM
- Bring the same Flutter codebase to Windows, macOS and Linux, and prepare iOS distribution.
- Adapt navigation and layouts for phones, tablets and desktop windows rather than merely stretching a phone screen.
- Add desktop keyboard shortcuts, window-size handling, file import/export and platform-specific packaging.
- Test each OS separately; do not claim support based on compilation alone.

PHASE 4 — OPTIONAL ACCOUNTS AND SECURE SYNC (NOT IMPLEMENTED)
- First document data flows, retention, account deletion and recovery.
- Use supported end-user authentication; do not build a custom password system.
- Require authentication on every personal-data API and derive owner identity server-side.
- Proposed entities: workspaces, typed items, per-item revision/version, updated_at, deleted_at tombstones, and per-device sync cursor.
- Support idempotent retries, conflict detection, safe merges, session expiry, logout and revocation.
- Never upload local records silently. Ask the user to opt in and choose merge/replace behavior before first sync.
- Test cross-user isolation, two-device edits, offline queues, conflict recovery, account deletion and backup restore before private beta.

PHASE 5 — PRIVACY, SECURITY AND PUBLIC RELEASE
- Publish plain-language privacy notice, access terms, support path, release notes and supported-platform matrix.
- Minimize collected data. Keep personal content out of analytics/logs by default.
- Use secure OS storage for tokens/secrets; never store secrets in plaintext preferences.
- Add dependency checks, signed release builds, crash reporting only with suitable privacy controls, migration/rollback guidance and a documented support process.
- Update the central YorpHives product catalogue only when each supported platform has evidence-backed test results.
- Future AI planning, cloud sync, bank integrations, billing and third-party integrations remain unavailable until implemented, tested and documented.

CURRENT STATUS — HONEST BASELINE
- The current /lifeos/ experience is a browser-based JavaScript prototype/PWA using browser localStorage.
- It is useful for validating interaction patterns and demonstrating the product, but it is not a native app.
- A separate Flutter source scaffold is documented in /lifeos/NATIVE-STARTER-STATUS.txt, but it has not been compiled or run in the available environment. No verified Flutter application, Android APK/AAB, iOS build, desktop installer, native notification system, account system or cloud sync has been delivered.
- Current prototype features include tasks, habits, goals, manual expenses/subscriptions, study/career items, reminders, document references, JSON backup/import and a PWA shell.
- PWA installation/offline behavior must not be represented as equivalent to a fully tested native application.
- Avoid highly sensitive information in the prototype. Preserve a verified backup before any future migration.
